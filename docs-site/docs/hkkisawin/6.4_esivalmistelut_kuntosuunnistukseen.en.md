# 6.4 Preparations for recreational orienteering

### 6.4 Preparations for recreational orienteering

The first
step is normally to define the competition's basic data and classes
in the usual way.

Recreational orienteering operating models 1 and 2 are based
on the program moving the competitor's data to a vacant place already in the
file. You should therefore create considerably more of these vacant places in advance
than there can be participants. This is done in the program's preparation mode with the option
"Entries/Add vacants". The vacants must be created as vacants. The program works best
when the vacants are created in an extra class whose course contains a
punching unit code that does not exist in the forest or. The vacant class can also be left
entirely without a course, but this may
cause puzzling error messages when the program is started in the middle of the event. The program tries
to create a vacant class automatically and places 20 participants in it in the highest places of the available
number range. The much more
numerous vacants needed in recreational orienteering can be created in this class generated by the program
at lower participant numbers.

Furthermore, for
subsequent operation it is best to create the vacants so that the last name field and
the club field are empty. The program always stores the participant's number as the first name.

If several computers are used, it is advisable to give each
its own range of the created vacant places by giving the parameter

`VAKANTTIALKU=nnn` 

Vacants can be created, for example, for numbers 1-2000,
and the two computers used can be given the start values 1 and 1000. The same numeric values
also affect the free Emit codes produced by the program, unless the parameter EMITALKU=nnn
is also given
, with which the number range can be changed
to another. Reserving a separate number range for each computer ensures that
the program does not select the same vacant record at different stations for
different participants, or the same number when automatically creating Emit codes
for saving after finishing. Creating the same code on two computers
leads to disruptions.

Operating model 3 is intended especially
for multi-day orienteering events, where participants receive their bib numbers at the competition office and
data entry is also handled at the competition office. Data entry does not need to be
complete before the performance, but in that case the name and other data are not
visible at the time of the performance; they only appear in the results
compiled later. The option *Entries / Entries*
starts in operating model 3 with settings suitable for data
entry at the competition office.
