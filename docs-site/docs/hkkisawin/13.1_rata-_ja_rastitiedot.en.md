# 13.1 Course and control data

### 13.1 Course and control data

The option *Preparation / Course data*
leads to the definition of course data and control punching unit codes, and to the
output of this data. This is handled as a separate preparation task, so
the program saves the data to files, from which it must be read separately
for use in the results service phase. When working in results service mode, however,
the course data of the active competition is automatically loaded for editing, and
it can be put into use after the file has been written with the button *Apply data*. Even during the results service it is
possible to view and edit other course data as well, when it is opened
separately and the button *Apply data* is not used.

Previously defined course data and punching unit codes must
be read for viewing using the relevant buttons, or on the page *Transfer files*, where course data produced by other programs
(Condes, OCAD) can also be read.

When data has been edited, it must first be saved
from the table to the program's memory and then separately to a file. This way
the consistency of the data can be checked before it is written to the file.

The program's old way of storing and using course data
was based on two text files, RADAT.LST and LEIMAT.LST. The new storage method is based on a single
XML file `radat<n>.xml`,
where `<n>` refers to the sequence number of the stage (e.g. radat1.xml). The file format used closely resembles
the IOF standard 2.0.3 for course data, but with the following restrictions
and exceptions:

- Each course variation is also an independent course.
  The program uses the name of the course variation as the course name.

  - The finish is usually handled as the last control, which must
    be given a numeric code and for which punching unit codes can also be defined.
    If there is no punching unit at the finish, the finish is nevertheless handled as a finish
    according to the IOF standard.

    - Fields have been added to the file indicating the nature
      of the finish and the reset advance (i.e. whether the reset takes place at the start time or before
      it).

      - The file can also store
        information on assigning a course to a class, following the IOF version 3.0
        definitions.

The buttons on the right-hand side of the form
are used to read and write the xml-format course data of my results programs.
Reading and writing the old text file formats of my programs
is requested from the menu under the option *File*. The tab described in chapter 13.4
can handle both the program's own XML files and several other
file formats.

If the program's working directory contains a course file in the new format,
the program uses it in the results service; otherwise the program reads the data in the old
format, if it is found. It is therefore essential to make sure that,
for example, the file radat1.xml is exactly what
is to be used in the first or only stage of the
competition.

In addition to the control and punching unit codes essential for the results service
itself, the course data includes coordinate and distance data,
and possibly the identification codes of the start and finish. These are needed if you want
to handle a map or use distance data, for example,
in split time outputs.

#### 13.1.1 How a competitor's course is determined

The course belonging to a competitor is determined either from the class name, from the assignment of a course
to the class, or from a course identifier stored for the competitor. The simplest procedure is
to define for each class a course whose name is the class name, in which case
the competitor's course is always the course of that class, regardless of any
course identifiers in the competitor data. This procedure cannot, however, be used
when the class has forked courses, for example butterfly loops. In that case
the course data must not include a course whose name is exactly the same as
that of the class; instead the different variations must be given names that are not
class names. The data of every competitor using these
courses must then contain the course
identifier.

When you want the same course to be used in several classes without making
copies of it for each class, there are two
options:

- The course can be assigned to a class on the tab
  *Classes*
  . The assignment data can
  also be read from an xml file conforming to IOF
  version 3.0.

  - The course identifier can be stored for every competitor
    using it.

In the latter case the course identifier must differ from all class names, none
of the classes concerned may have a course named after the class,
and the identifier of the course must be stored for all entrants of these classes. In the former
case, too, it is clearer to use an identifier that differs from the
course names.

A course defined separately for each class offers
flexibility, for example, when it is later decided to make the courses
different, but the drawback of this solution is that last-minute
course changes and corrections during the competition
must be made to every course they
concern.
